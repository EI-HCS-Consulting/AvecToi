**⚠️ Règle Git STRICTE (CLAUDE.md) :** chaque modification, même un correctif ponctuel, part sur une branche neuve (depuis `origin/main` à jour) et se termine par sa propre PR poussée sur GitHub — jamais de nouveau commit ajouté à une branche dont la PR est déjà mergée. **Autorisation permanente : commit + push + PR dès qu'une tâche de code est terminée et vérifiée, sans attendre que l'utilisateur le redemande.** **L'utilisateur merge lui-même, puis teste** (le merge déclenche la publication OTA — sauf nouvelle dépendance native, qui nécessite un `eas build` + réinstallation complète). Toujours vérifier l'état réel d'une PR via `gh pr view <n> --json state,url` plutôt que de supposer.

**⚠️ Convention UI (CLAUDE.md, "Conventions UI") — renforcée ce cycle :** toute nouvelle confirmation *ou tout nouveau message purement informatif à un seul bouton* utilise `ConfirmModal` (jamais `Alert.alert` natif, y compris pour un simple « J'ai compris ») ; tout nouveau bouton reprend les couleurs/emoji/style déjà en usage à l'écran ; toute notification éphémère réutilise le pattern `showToast` existant. Ce point a été manqué une fois ce cycle (voir §1) puis corrigé — vérifier systématiquement `grep Alert.alert` sur tout fichier touché par un nouveau popup avant de considérer la tâche terminée.

## 1. Objectif de la session
Trois demandes distinctes traitées dans la continuité d'une même session de code (PR déjà mergées avant le début de la portion documentaire de cette session) :
1. **Report d'échéance sur les items suivants d'une checklist** (`components/Entraide.tsx`, `components/MyChecklist.tsx`) — demande initiale : pouvoir fixer une seule fois une échéance et la reporter sur tous les items suivants du wizard séquentiel, sans avoir à la ressaisir manuellement sur chacun des jusqu'à 14 items d'une checklist. Implémenté dans les deux wizards indépendants de l'app (Entraide et Mon Compte → Checklist personnelle, qui ne partagent pas d'état) via `propagateChecklistWizardDate()` / `propagateImportWizardDate()` : un bouton « 📌 Reporter cette échéance sur les items suivants » sur chaque popup d'échéance (sauf le dernier item) copie la date de l'item courant sur tous les items restants — `Entraide.tsx` recalcule en plus le drapeau auto-urgent (`isUrgentWindow`) pour chaque item propagé, cohérent avec la logique auto-urgent déjà en place ; `MyChecklist.tsx` n'a pas cette logique et reste plus simple. **PR #464 mergée.**
2. **Correction du popup de confirmation** — la première version de #464 utilisait `Alert.alert()` (natif) pour le message de confirmation « Échéance reportée » après un appui sur le bouton ci-dessus. L'utilisateur a signalé que ce popup devait suivre le même design que le reste de l'app. Remplacé par `ConfirmModal` en mode `singleButton` (icône 📌, `destructive={false}`, état local `dateReportedConfirm`) dans les deux fichiers, en reprenant exactement le pattern déjà existant `fullyImportedTplName` de `MyChecklist.tsx`. **PR #465 mergée** — nécessitait une branche neuve (`fix/checklist-echeance-popup-design`) depuis `origin/main` à jour, car la branche de #464 était déjà mergée (règle Git stricte du repo).
3. **Renforcement de la convention anti-`Alert.alert()`** — bien que `CLAUDE.md` interdise déjà explicitement `Alert.alert()` natif pour tout nouveau popup (section « Conventions UI »), cette règle a été manquée en session malgré sa présence écrite, probablement suite à une compaction de contexte ayant fait sortir une lecture antérieure de `CLAUDE.md` du contexte actif. Deux actions correctives, sur demande explicite de l'utilisateur (« ajoute cette consigne dans les documents adéquates ») :
   - `CLAUDE.md` : formulation renforcée pour fermer explicitement la faille (un popup purement informatif à un seul bouton était implicitement traité comme « pas une vraie confirmation » et donc exempté à tort) — voir section « Conventions UI » et le rappel dans « Commande handoff ».
